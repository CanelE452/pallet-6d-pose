### ★계약 감사 — 실증으로 확정한 것

세 도메인의 키포인트 의미가 같은지를 **순열 재계산이 아니라 배포 PnP reprojection** 으로
확인했다 (`pose6d_adapter.object_points` 순서 그대로, near/far 뒤집은 대조군과 비교).

```
도메인                as-is median    near/far swap    비율
────────────────────────────────────────────────────────────
G  paper_release        0.00 px          8.03 px       inf
T  v1 palletobj         3.49 px         23.76 px       6.8x
T  v2 palletobj         3.75 px         23.14 px       6.2x
R  real manual_kps      1.53 px         31.16 px      20.4x
```
→ 0~3 이 실제 near face 이고 배포 3D 모델점 순서와 일치. **변환 함수 불필요.**

**T 의 dims 필드 순서를 실증으로 확정**: `cuboid_dimensions_m = [1.1, 1.3, 0.12]` 은
문서가 없었는데, 네 해석을 전부 PnP 로 돌려 `[depth, width, height]` 로 판명
(median 0.00px, 나머지는 3.8~109px). registry 는 이 순서로 읽는다.

**★`convert_to_camera_facing_v4.py` 를 G/T 에 재적용 금지**. 이 스크립트의 2D polygon-area
휴리스틱은 G 표본 400 중 159(40%)를 non-identity 로 판정하지만, G 의 as-is reprojection 이
0.00px 이므로 **틀린 쪽은 스크립트**다 (저앙각에서 무너짐). 다시 돌리면 데이터가 깨진다.

### ★padding 계약 — G 는 840x680 이 아니다

G 는 해상도가 4종(640x480 / 960x540 / 720x480 / 560x560)이라 +100px 해도 크기가 제각각이다.
사용자 결정(08-14): **해상도와 무관하게 각 이미지에 +100px**. YOLO 정규화 좌표는 이미지별
기준이라 학습에 문제없고, contract 의 `padded_width/height: 840/680` 은 640x480 입력에만
해당한다고 명시했다.

단위 테스트 전원 통과:
```
왕복 오차       1.14e-13 px  (기준 1e-4)
PnP 등가성      |dt| 5.7e-13 m, |drvec| 2.6e-13 rad
negative control  좌표계를 섞으면 t 가 최대 3.60 m 어긋남 → 테스트가 vacuous 하지 않음
```

### ★medium batch 확정 — 이 GPU 에서 m 은 batch 8 이 한계 [확인]

probe 를 믿고 batch 32 로 시작했다가 세 번 재시작했다. 결론부터:

```
시도                                              결과
──────────────────────────────────────────────────────────────────
1차  batch 32 (probe peak 8.34 GiB 로 "통과")      즉시 OOM → Ultralytics 가
                                                  자동으로 32→16→8 축소해 진행
2차  깨끗한 GPU 8,829 MiB + expandable_segments    batch 16 즉시 OOM → 8 로 축소
3차  batch 8 명시                                  정상. 6,290 MiB, epoch 1,698 s
```

**단편화가 아니라 순수 용량 부족이다.** 2026-04-10 의 allocator 단편화 사례가 떠올라
`PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True` 를 넣었는데도 16 이 실패했고,
batch 8 이 6.2 GB 를 쓰므로 16 이면 약 12 GB — 10 GB 카드에 원리적으로 안 들어간다.

★ **내 probe 설계 결함 2가지**
```
1. fraction=0.004(약 300장) · val=False 로 쟀다.
   실학습은 73,916장 + val 4,009장 + worker 4개가 더 붙는다.
2. 판정 기준이 "OOM 예외만 안 나면 ok=true" 였다.
   peak 8.34 / 가용 8.9 GiB = 94% 는 통과가 아니라 경계선인데 통과로 적었다.
   → 안전 마진(예: 85% 이하)과 val 로더를 넣었어야 했다.
```

★ **Ultralytics 는 OOM 시 batch 를 자동 축소한다** (32→16→8, 최대 3회).
프롬프트의 "batch 를 자동으로 변경하지 않는다" 를 라이브러리가 무시하는 셈이라,
`args.yaml` 과 run 이름은 요청값(b32)인데 실제는 b8 이 된다. **step 수로 검증할 것**
(73,916/batch). 로그의 `Reducing to batch` 경고를 감시에 반드시 포함한다.

★ **그래도 nano 와 비교는 유효하다** — `nbs=64` 가 accumulate 를 맞춰준다.
```
              batch   accumulate   유효 batch   lr0
nano            32         2           64       0.01
medium           8         8           64       0.01
```
optimizer 가 보는 조건은 동일. 차이는 BatchNorm 통계가 batch 8 기준이라 noisy 한 점뿐이며
model card 에 명시한다. (처음에 "lr 이 4배 과다" 로 오판했으나 nbs 때문에 틀렸다.)

최종 run: `runs/stage_a_m_640_b8_seed42/` (epoch 1: 1,698 s / Pose mAP50-95 0.7732)
중단본 보존: `_aborted_m_actual_b8_20260815/` (1차) · `_aborted_m_b16_oom_20260815/` (2차)
60 epoch 약 25~28 h 예상 → 08-16 아침.

(과제 1순위 지표). 재렌더는 범위 밖이라 이번엔 그대로 진행했고, real finetune 후 recall 이

### ★재편이 놓친 것 — dirname 중첩으로 깊이를 세는 코드

`challenge/` 에서 멈춰 있었다. 그 상태로 repo 상대경로를 붙이면

```
→ dirname 을 하나씩 더 감싸고 사유를 주석으로 남김
```
**찾은 방법**: 정규식이 아니라 ROOT/REPO 대입식을 실제로 평가해 저장소 루트가 나오는지

## yolo26n-pose 추론 시각화에 yaw 추가 + dims 불일치 실측

### 변경 파일

`challenge/pallet_jetson_deploy/infer_fps.py` — **그리기 경로만** 수정. PnP·keypoint
순서·dims 등 "검증된 로직" 은 일절 건드리지 않았다.

- `yaw_from_R(R)` 신규 (draw_axes 위). `degrees(arctan2(R[0,2], R[2,2]))`.
- PnP 성공 HUD: `PnP OK pts=N z=N.NNm` → `... yaw=+N.Ndeg`.

yaw 계산은 draw 블록 안에 있어 headless FPS 측정에는 들어가지 않는다.

### yaw 정의는 두 곳에서 180° 달랐다

```
출처                                        공식                                  정렬완료
────────────────────────────────────────────────────────────────────────────────────────
pose6d_adapter.pose6d_to_align_vars (정본)  atan2(R[0][2],R[2][2]) + 180 → wrap    psi = 0
run_dope_live.py:331 (시각화)               atan2(R[0,2],R[2,2])                   ±180
```

adapter 의 `+180` 은 2026-05-27 실차 디버깅 fix (psi=-165.6° 로 나와 리프터가 거의
안 움직였음). 두 파일의 **3D 모델 좌표계가 서로 Y·Z 부호 반대**(adapter=+Y up/front +Z,
infer_fps=+Y down/near -Z)라 그 180° 가 상쇄된다.

추측으로 넘기지 않고 수치 대조했다 — 같은 2D 키포인트를 두 3D 모델로 각각 PnP 해서
비교(dims 는 1.10/1.30/0.12 로 통일해 순수 convention 차이만 봄):

```
n=24 (capture0403noapril)     median |Δ| vs adapter psi
──────────────────────────────────────────────────────
yaw = atan2 (offset 없음)     0.000 deg    ← 채택
yaw = atan2 + 180             180.000 deg
```

reproj 도 두 모델이 프레임마다 동일 = 같은 pose 를 다른 좌표계로 표현한 것.
검증 스크립트는 scratchpad (`verify_yaw_convention.py`) — 일회성이라 repo 미포함.

### dims 는 실제로 틀려 있다 (미수정, 보고만)

contract 가 `view_dependent_width_depth: true` 라고 명시하는데 infer_fps.py 는 한 쌍
고정이다. capture0403noapril 188 프레임 실측:

```
dims 후보                    reproj med   reproj mean   z med(m)   best-fit
──────────────────────────────────────────────────────────────────────────
A (1.10,1.30,0.11) 현재          5.79         6.78       2.236     31/188
B (1.30,1.10,0.12) contract      4.24         4.20       2.484    127/188
C (1.10,1.30,0.12) alternate     6.13         6.99       2.240     30/188

A 대비 yaw 차이:  A vs B  median 3.22 deg / max 7.26 deg
                  A vs C  median 0.00 deg / max 0.11 deg
```

**B 가 188 중 127 프레임에서 최적**인데 현재 코드는 A 를 쓴다. height 는 yaw 에 거의
영향이 없고(A vs C = 0.00°), width/depth 스왑이 전부다(A vs B = 3.22°). 즉 화면의
yaw 에 median 3.2° bias 가 실려 있다. 프레임별로 두 후보를 풀어 reproj 낮은 쪽을
고르는 게 정공법이나, 사용자 요청 범위 밖이라 이번엔 손대지 않았다.

### yaw 화살표가 뒤로 향하던 원인 + yaw-only 모드

사용자가 "yaw 가 뒤집혀 보인다, 카메라 기준 뒤로 보여" 라고 지적. 3d-expert 위임으로 확정.

**원인**: `draw_axes` 의 파란 Z 화살표는 local **+Z = far face** 쪽이다. 이 파일 모델은
near(0~3, fork-pocket 면) = `z=-d/2` 이므로 **팔레트 정면 = local −Z**. +Z 를 그리면
항상 소실점 방향(화면 안쪽)으로 뻗는다. 실측: 카메라 pitch-down 15°/Z=3m 에서
near 평균 z = 2.36m vs far 3.61m → 0~3 이 카메라 쪽이 맞다.

전 세션 대조도 재확인됨: `D=diag(1,-1,-1)` 로 infer 모델 → adapter 모델 일치(오차 2.8e-17),
φ = −60~+179 전 구간에서 `yaw_from_R == adapter psi` (diff 0.0000).

**내가 어제 쓴 docstring 이 틀렸다** — "ψ>0 → 팔레트 정면이 카메라 우측" 은 반대다.
ψ 는 far 축(+Z, 지게차가 향해야 할 heading)의 방위각이라, ψ=+30 이면 정면 법선은
`(−0.5,·,−0.866)` = **카메라 좌측**이고 지게차가 **우회전**해야 한다. `align.py:425/431/433`
의 `ψ>0 → direction=+1 → ROT_RIGHT` 와 정합. **ψ 공식·부호는 그대로 두고 문구만 수정.**
같은 오류 문구가 `pose6d_adapter.py:74` 에도 있다(다른 repo라 미수정, 보고만).

**변경** (`challenge/pallet_jetson_deploy/infer_fps.py`, 그리기 경로만):

- `yaw_from_R` docstring 문구 정정 (위 내용).
- `draw_yaw_arrow(img,R,t,K,length=0.6,...)` 신규 — centroid → local **−Z** 화살표 1개.
  투영 길이 < `min_px`(14px) 면 ⊙ 로 그려 "정대면" 표시. 저앙각에서 화살표가 0px 로
  붕괴하기 때문 (Z=3m/L=0.6m: ψ=0·앙각0° → 0.0px, 앙각3° → 8.0px, 앙각8° → 21.3px,
  ψ=30°·앙각0° → 74.3px). real 94% 가 저앙각(<8°)이라 정렬 근처에서 실제로 발생.
- `--yaw-only` 플래그 — cuboid + yaw 화살표 + `yaw=±N.Ndeg` 만. keypoint 점/번호,
  XYZ 3축, `frame N DET`, `PnP OK pts z`, `infer NN FPS` 생략. **기본 동작은 불변**
  (Jetson 배포용이고 문서 3곳이 이 스크립트를 참조 중).

화살표 방위각은 정의상 ψ+180° 다 — 모순이 아니라 반대축이다. ψ 는 진입 heading,
화살표는 팔레트가 바라보는 쪽. 둘을 한 화살표로 동시에 만족시킬 수 없다.

### 데이터를 실제로 망가뜨리던 것 [상]

  `annotate.py` 의 `f`/manip `S` 에도 있어 함께 수정.

  `kps_2d` 를 건드리지 않게 바꿈.

### roll/pitch/yaw 전체 표시

3d-expert 위임으로 오일러 순서 확정. **내재 Y-X-Z (`R = Ry(yaw) @ Rx(pitch) @ Rz(roll)`)**
에서 `R[:,2] = (sy*cp, -sp, cy*cp)` 이므로 `atan2(R02,R22) == yaw` 가 cos(pitch)>0 인 한
항등 — Tait-Bryan 6 종 중 기존 `yaw_from_R` 과 값·부호가 같은 **유일한** 순서다.
(X-Y-Z 를 쓰면 `atan2(R02,R22)=atan2(sy, cp·cy) ≠ yaw` 로 깨진다.)

검증(각 200k 샘플): round-trip max 5.7e-14° / R 복원 max 1.6e-13 / **|yaw_new −
yaw_from_R| = 0.000e+00°** (gimbal band 포함). 따라서 align.py 로 가는 ψ 부호 규약 불변.

부호: `pitch>0` = far(4~7) 쪽이 위로 들림 / `roll>0` = 폭축 +X_local 이 아래 = 화면상
시계방향. **pitch·roll 은 카메라 상대값**이라 마운트 틸트가 섞인다(지면 기준이 필요하면
캘리브된 하향각을 빼야 함 — 미측정). yaw 는 Y 축 회전이 outermost 라 그 보정과 분리된다.

**변경** (`infer_fps.py`, 그리기 경로만):
- `roll_pitch_yaw_from_R(R)` 신규.
- `draw_yaw_arrow` length 0.6 → **2.0m**, min_px 14 → 6 (⊙ 는 이제 원리적 붕괴에만).
- `draw_yaw_compass` / `draw_attitude_gauge` / `draw_rpy_panel` 신규 — 우하단 고정 위젯.
  나침반은 **화면좌표계** 위젯이라 원근과 무관하게 크기 고정. 바늘 = 삽입축(near→far)
  = 지게차가 향해야 할 heading, yaw>0 이면 우측 → align.py ROT_RIGHT 와 화면이 자동 일치.
  deadband 3° 로 ALIGNED / TURN LEFT / TURN RIGHT.
- `--yaw-only` 모드: cuboid + 화살표 + 위젯 + `roll/pitch/yaw` 숫자 한 줄. 기본 모드 불변.

렌더 비용 0.48ms/frame (draw 경로만, inference FPS 무영향).

**눈 검증**: 프레임 60/150/220 을 개별 로드해 확인. 1 차본에서 숫자가 좌상단·우하단에
중복돼 패널 숫자를 제거하고 `roll/pitch` 라벨로 대체. 화살표 방향(정면=우측)과 나침반
