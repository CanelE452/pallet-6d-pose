## 1. `challenge/pallet_jetson_deploy/infer_fps.py` (수정)

Jetson 배포용 standalone. **그리기 경로 + 모델 로딩만** 손댔고 PnP·keypoint 순서·3D
모델·dims 등 "검증된 로직" 은 건드리지 않았다.

```
항목                    Before                      After
──────────────────────────────────────────────────────────────────────────────
모델 로딩               YOLO(args.model)            YOLO(args.model, task="pose")
yaw 각도                없음                        yaw_from_R()
roll/pitch              없음                        roll_pitch_yaw_from_R()
방향 표시               draw_axes XYZ 3축 0.5m      + draw_yaw_arrow (local -Z, 2.0m)
draw_axes 시그니처      (img,R,t,K,length)          + viewer_axes, labels
  └ Y 축                local +Y (OpenCV down)      viewer_axes 면 -Y (up)
  └ Z 축                local +Z (far, 뒤)          viewer_axes 면 -Z (front)
자세 위젯               없음                        나침반 + roll/pitch 자세계 (우하단 고정)
표시 모드               단일                        --yaw-only 플래그 (기본 동작 불변)
```

**이유**

1. **`task="pose"` 가 최우선 수정이다.** `.engine`/`.onnx` 는 메타에 task 가 없어
   ultralytics 가 detect 로 가정하고, 그러면 `r.keypoints` 가 None 이라 **검출률이
   0% 로 떨어진다**. `.pt` 는 멀쩡해서 로컬 테스트로는 절대 안 잡히고 Jetson 에서
   engine 을 물리는 순간에만 터진다. 3080 TRT FP16 에서 det 0/400 → 383/400 으로 회복.
2. **화살표 방향** — 이 파일 모델은 near face(0~3, fork-pocket) = `z=-d/2` 라
   팔레트 정면이 **local −Z** 다. 기존 파란 +Z 축은 far 쪽이라 늘 소실점 방향으로
   뻗었다(사용자 "카메라 기준 뒤로 보인다"). 실측: near 평균 z 2.36m vs far 3.61m.
3. **화살표 길이 0.6 → 2.0m** — 0.6m 일 때 553 프레임 중 65.8% 가 14px 미만이라 ⊙ 로
   그려졌다. ⊙ 그룹의 |yaw|·앙각·거리가 전체와 **동일**했으므로 원인은 각도가 아니라
   거리(median 3.72m) 대비 짧은 길이였다.
4. **오일러 순서 = 내재 Y-X-Z** — 이 순서에서만 `atan2(R02,R22) == yaw` 가 항등이라
   기존 `yaw_from_R`(= deployment psi) 과 값·부호가 같다(uniform SO(3) 200k 대조
   0.000e+00). 다른 순서면 `align.py` 의 `psi>0 → ROT_RIGHT` 분기가 깨진다.
5. **나침반 위젯** — 정면 벡터의 화면 투영은 카메라를 정확히 향할 때 길이가 0 이라
   방향이 정의되지 않는다(원리적 한계). 화면좌표계 위젯으로 빼면 원근과 무관하다.
6. **docstring 정정** — 내가 08-15 에 쓴 "psi>0 → 팔레트 정면이 카메라 우측" 은
   반대다. 정면 법선은 **좌측**이고 지게차가 **우회전**해야 한다.

## ★정정 — PnP cuboid 왜곡의 원인은 내 그리기 버그였다

사용자: "점은 제대로 찍혔는데 왜 PnP가 제대로 안 되지?" (`[1016×1220×120] 목재 파렛트`)

**내 1차 진단이 틀렸다.** "keypoint 높이비가 실제보다 37% 과대(화면 0.162 vs 실제 0.118)라
PnP 가 그 모순을 자세 기울임으로 흡수한다" 고 답했는데, 높이비 수치 자체는 맞지만
왜곡의 원인이 아니었다.

**진짜 원인** (`challenge/yolo_pose_one_model/scripts/internet_pallet_yolo_ab.py:draw()`):

```
Before   X = APNP.make_pallet_keypoints_3d(*dims)[:8]        # 파일명 dims
After    X = APNP.make_pallet_keypoints_3d(*pose["dims"])[:8] # pose 가 실제로 쓴 dims
```

`solve_pose(auto_swap_dims=True)` 는 as-given 과 W/D swap 을 모두 풀어 reproj 낮은 쪽을
고른다. 반환된 `(R,t)` 는 **선택된 `pose["dims"]` 에만 맞는다**. 그런데 그리기 쪽은
파일명 dims 로 상자를 다시 만들어 투영했으니 pose 와 다른 모양을 그렸다 —
큐보이드가 39px(최대 82px) 어긋났다.

**헤더의 reproj 5.49px 은 정상값이었다.** PnP 가 푼 자세의 오차이고, 그림만 다른 상자를
그리고 있었다. 즉 **숫자와 그림이 따로 놀았고**, 나는 그 불일치를 모델·keypoint 탓으로
돌렸다. `auto_swap_dims` 가 dims 를 바꿀 수 있다는 걸 알고도(그 직전 진단에서 스왑을
배제하려 직접 확인했다) 그리기 경로가 같은 dims 를 써야 한다는 데 생각이 닿지 않았다.

**교훈**: 지표(reproj)와 시각화가 어긋나면 **둘 중 하나가 다른 입력을 쓰고 있는지부터**
본다. 모델을 의심하기 전에 파이프라인 내부 일관성을 먼저 확인해야 했다.

수정 후 재실행: base 의 큐보이드가 팔레트에 맞는다(눈 검증). ft 는 여전히 어긋나는데
이쪽은 그리기가 아니라 keypoint 자체가 부정확한 것이다(reproj 7.88px) — **base 우세
판정은 유지**. 10 장 산출물 전부 재생성했다.

### "foundation model 이라 불러도 되나" → **불가**

사용자 질문. 정의 6 축 어디로도 닿지 않는다: 학습 데이터(합성 74k + real 400 vs 웹 스케일),
다양성(팔레트 1종 vs 무제한), 태스크(6D pose 단일 vs 다운스트림 범용), zero-shot 평가
(인터넷 9장 GT 없음 vs 벤치마크 수십 개), 파라미터(3.04M vs 수억~수십억), 조건부 일반화(불가).

**내가 앞서 "일반화 확인" 이라고 보고한 것의 실제 무게도 정정했다**: n=9(실질 인스턴스 4~5종),
GT 없어 정량 불가, pose 는 실제로 틀렸던 상태(그 직후 그리기 버그로 판명), 실내 창고에서는
4장 중 1장 오검출. 말할 수 있는 건 **"detection 이 처음 본 팔레트로 전이된다"** 까지고,
**"6D pose 가 일반화된다"는 근거가 없다.**

쓸 수 있는 표현: `cross-instance generalization` / **`category-level pose estimation`**
(NOCS 계열 표준 용어, 지금 목표와 정확히 일치) / `zero-shot detection transfer`.
쓰면 안 되는 것: `foundation model` / `general-purpose` / `universal`.
