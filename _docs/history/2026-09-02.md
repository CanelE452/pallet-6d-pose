## M1 의 DOPE 행을 채웠다 — evaluator 에 offline prediction 경로

M1 이 2행(YOLO26 R0 · Proposed)뿐이라 "main method comparison" 이라 부르기 어려웠다.
DOPE 는 checkpoint 가 있는데도 못 넣고 있었다 — evaluator 가 Ultralytics 전용이라서다.

```
challenge/evaluation_v2/paper_real_eval.py:1724   self.model = YOLO(str(weights), task="pose")
```

**해결 방식**: DOPE 전용 채점기를 따로 만들지 않았다. 그러면 M1 의 행들이 서로 다른
자로 잰 값이 되어 비교가 성립하지 않는다. 대신 evaluator 에 예측 주입 경로를 열었다.

```
Before                          After
──────────────────────────────────────────────────────────────────────────
predictor = _Ultralytics        --predictions 있으면 _CachedPredictor
Predictor(weights, device)      없으면 기존 _UltralyticsPredictor (기본 동작 불변)
(분기 없음)                     weights 는 provenance 로 계속 기록
                                selection_policy = OFFLINE_CACHED_PREDICTIONS
```

`_CachedPredictor` 는 `image path -> [{score, box_xyxy, keypoints_xy}]` 를 읽어
`_UltralyticsPredictor.predict()` 와 **같은 튜플 형태**를 돌려준다. 그래서 AP·keypoint·
subgroup 채점 코드는 한 줄도 바뀌지 않는다.

### 신규 `scripts/self_training_yolo/dump_dope_predictions.py`

추론 규약은 지어내지 않고 정본 함수를 그대로 썼다.

```

paper_s2_real_eval.E.load_model / pad_frame / belief_to_orig_pad
```

reflect-padding 은 선택이 아니다 — plain squash 는 truncation·근접에서 체계적
과소검출을 만들어 DOPE 를 부당하게 나쁘게 만든다 (2회 교정 이력).

`mc_dump_dope.py` 는 쓰지 않았다. 그건 **다른 모델**(SplitLate multihead,
`weights/paper_s2/...`)용이고 161장 canonical 셋에 묶여 있다 `[확인]`.

## ★두 제안 필터의 단독 ablation — 누적 표로는 못 뽑던 것

사용자 지적: "flip 이랑 projection 각각 해보는 거" 를 했느냐.
**안 했었다.** 기존 arm 구성이 이랬다.

```
reproj 단독    F2 / R3_CONF_REPROJ    ✅
removal 단독   F3 / R4_CONF_REMOVE    ✅
flip 단독      (없음)                  ❌
removal+flip   F4 / R5_PROPOSED       ✅
```

M3 는 누적(R2→R4→R5)이라 `R4→R5` 는 **removal 이 이미 걸린 상태의 flip** 이지
flip 단독 효과가 아니다. 그래서 flip 단독 arm 을 만들고 2x2 를 완성했다.

### 신규 F5_CONF_FLIP + R6_CONF_FLIP

```
Before                                   After
──────────────────────────────────────────────────────────────────
ARMS = F0,F1,F2,F3,F4                    + F5_CONF_FLIP (flip 단독)
F4: removal_ok AND s_flip<=tau           flip_ok 를 먼저 계산해 F5 와 공유
manifest 5종                             manifest 6종
```

기존 F0~F4 manifest 는 **비트 동일**하게 재현됐다 (F4 sha 0df3a640 unchanged) `[확인]`.

### ★해석 — 주장을 다시 좁혀야 한다

```
keypoint-removal 단독   Δ +0.007   ← 효과 없음 (자기 std 0.045 안)
horizontal-flip 단독    Δ -0.060   ← std 0.076 안. 단독으로는 산포를 못 넘는다
둘 다 (Proposed)        Δ -0.123   ← std 0.014. 산포를 넘는다

단독 합 Δ -0.053  vs  실제 조합 Δ -0.123   →  상호작용 Δ -0.070
```

**어느 필터도 단독으로는 자기 replicate 산포를 못 넘는다. 조합만 넘는다.**
상호작용 항(-0.070)이 flip 단독 기여(-0.060)보다 크다 — 두 필터는 각자
독립적으로 기여하는 게 아니라 **함께일 때만** 효과가 나온다.

따라서 "flip 이 주 기여자" 라고 쓰면 안 된다. 앞서 누적 표에서 `R4→R5 Δ -0.132`
를 보고 그렇게 읽었는데, 그건 removal 이 먼저 걸린 조건에서의 값이었다.

Proposed 의 replicate std 가 0.014 로 네 칸 중 가장 작다는 점도 같이 남긴다 —
조합이 학습 신호를 안정화한다는 해석과 일관되지만 replicate 3 개라 분산 자체를
주장하지는 않는다.
