못 하지만 봉합하지 않고 남긴다.

### 확인만 하고 코드 변경 없음

- **YOLO26 은 2단계(box -> crop -> keypoint)가 아니다.** `Pose26.forward_head` 에서
  `pose_head` 가 백본 특징 `x` 를 받고, `kpts_decode` 는 anchor·stride 만 쓴다.
  실증: 예측 keypoint 가 예측 box 밖으로 나간 것이 6프레임에서 **19/54(35%)**.
  box 는 "어느 anchor 의 답을 채택할지" 를 고르는 선택 장치일 뿐이다.

- **YOLO26 에 adaptive keypoint uncertainty 가 실재한다.** RLE(Residual
  Log-likelihood Estimation) + RealNVP flow, keypoint 별 sigma_x/sigma_y.
  `error = (pred - gt) / sigma`. 우리 체크포인트에 `cv4_sigma` 12개 +
  `flow_model` 75개가 살아 있고 `rle=1.0` 으로 학습됐다.
  ★단 `if self.training:` 안에서만 출력되고 `fuse()` 가 그 head 를 지운다.
  train 모드 forward 로 꺼내보면 코너별로 값이 다르다(kp5 sy 0.523 vs kp7 0.917).
  **현재 우리 PnP 는 sigma 를 안 쓴다** — 제목에 넣으려면 추론에서 꺼내
  sigma 가중 PnP 로 연결해야 기여가 된다.

폴더 이름과 session metadata가 목적지를 정한다 — 사람이 매번 고르지 않는다.

```
incoming/annotations/<session>__<material>/  +  세션 session.json 의 lighting
    -> final/positive/sessions/<material>_<lighting>_01
```

material 은 사용자가 저장할 때 고른 폴더에서, lighting 은 세션 메타에서 온다.
둘 다 기록된 사실이라 추론이 아니다. 근거가 없으면 건너뛴다(목적지 안 지어냄).
같은 SHA image는 독립 copy를 재사용한다. 같은 stem인데 SHA가 다르면 덮어쓰지 않고
collision으로 중단한다. 재저장한 JSON/overlay/condition tag는 destination에도
갱신하며, CLI batch 경로는 과거 누락분 복구용이다.

### 저장 훅에 배선

`eval_dataset_status.refresh_after_annotation`은 refresh 전에
`promote_incoming_annotation`을 호출해 **방금 저장한 한 frame만** 동기화한다.
편입 실패가 저장을 막지는 않되 WARN을 남긴다. 세션 일괄 condition 적용 때만 해당
staging session의 완성 annotation 전체 tag를 한 번 동기화한다.

검증: material×lighting 네 조합, JPG, targeted stem, 재저장, 삭제, image SHA collision,
세션 일괄 tag, package import 회귀 테스트를 추가했다.

### self-training exposure contract 동결 — filter 만으로는 부족하다

**신규** `scripts/self_training_yolo/freeze_exposure_contract.py`

self-training strength 는 filter 가 아니라 네 축이 정한다: pseudo sampling fraction,
pseudo loss weight, total optimizer updates, teacher refresh rounds.
filter 를 비교하려면 나머지 셋이 전 arm 에서 같아야 한다.

```
main_pseudo_fraction        0.50        synthetic 0.50
lambda_pseudo               1.0         (탐색하지 않는다 — knob 는 fraction 하나)
teacher_refresh             false       teacher_rounds 1 (static teacher)
batch                       32
lr0                         0.002
TOTAL_UPDATES               900         = 10 epoch x 90 update
pseudo exposures            14,400      synthetic exposures 14,400
epoch 물리 크기             1440 pseudo + 1440 synthetic = 2880
작은 pool                   with replacement 로 고정 슬롯을 채운다
```

epoch 이 아니라 **update 를 맞춘다**. arm 마다 accepted unique PL 수가 다르므로
"같은 epoch" 은 공정 비교가 아니다. 한 epoch 의 물리적 크기 자체를 고정했다.

**TOTAL_UPDATES 를 900 으로 고른 근거 (PAPER_EVAL 을 보지 않았다)**

`ADAPT_N0_15EP_SEED42` 는 negative 0 · pseudo 0 인 **synthetic replay 전용 control**
인데도 night 검출을 잃었다 (any-cbox 23 → 19 frames, 2026-08-25 기록).
그 레시피는 13,554 x 15ep / 32 = **6,353 updates @ lr0 0.002** 였다.

```
reference (열화 확인)   6,353 updates @ lr0 0.002
선택                      900 updates @ lr0 0.002   = 14.2%
```

LR 은 repo 확립값 0.002 를 유지했다 — LR 과 update 수를 동시에 바꾸면 원인을 못 가른다.
이 예산이 충분히 보수적인지는 **가정하지 않고 R0-CONT 가 측정**한다.

**신규 control arm — R0-CONT**

같은 init·LR·augmentation·batch·TOTAL_UPDATES 를 쓰되 pseudo-real exposure 0,
그 자리를 synthetic replay 로 채운다. 추가 최적화 자체의 효과와 real pseudo-label
adaptation 효과를 분리한다. 이게 없으면 `R0 → R1` 차이 중 얼마가 그냥 더 돌린
탓인지 알 수 없다.

학습 arm 이 5개에서 **6개**가 됐다: R0-CONT, R1, R2, R3, R4, R5.

**matching semantics 를 분리**

```
MAIN         EXPOSURE-MATCHED          updates / pseudo exposure / synthetic exposure 동일
Appendix A2  UNIQUE-QUANTITY-MATCHED   unique PL 개수 동일
```

혼동하지 않는다. A12(strength sensitivity, pseudo fraction 0.25/0.50/0.75)를
EXPERIMENTS.md 에 추가했고 MAIN row 는 결과와 무관하게 0.50 고정이다.

### ★정정 — ultralytics `seed` 는 학습을 바꾸지 않는다 (내 앞선 판정이 틀렸다)

§29 조건이 충족돼(아래) seed 43/44 를 4 arm 씩 돌렸다.

```
M2 primary(detection mean)   R0 0.9200  <  R1 0.9657  <  R5 0.9729
Daytime  R0 1.000 → R5 0.986  (Δ -0.014)
Nighttime R0 0.840 → R5 0.960 (Δ +0.120)   catastrophic degradation 없음
```

8 run 을 다 돌리고 평가했더니 **seed 43·44 가 seed 42 와 모든 지표에서 비트 동일**했다.

**내가 앞서 "seed 는 실제로 학습을 바꾼다 `[확인]`" 이라고 한 것은 틀렸다.**
1 epoch probe 에서 checkpoint **파일 SHA** 가 다른 것만 보고 단정했는데,
`.pt` 안에는 `args`(= seed 값)도 들어 있어 파일 해시는 당연히 달라진다.
memory 의 [ultralytics seed 가 dataloader 에 안 간다] 가 "replicate 는 **텐서 비교**로
검증" 이라고 적어 둔 이유가 바로 이것이고, 나는 그 지시를 따르지 않았다.

텐서로 다시 확인한 결과:

```
                     bit-identical   max|Δw|
─────────────────────────────────────────────
seed42 vs seed43          True       0.000e+00
seed42 vs seed44          True       0.000e+00
per-frame 예측 CSV        3개 해시 동일
```

`deterministic=True` 인데도 파일 해시만 달랐던 것이다. 가중치는 완전히 같다.

→ **ultralytics `seed` 만으로는 repeatability 를 주장할 수 없다.** seed 8 run 은
독립 반복이 아니므로 mean±std 를 만들지 않는다.

**진짜 replicate 로 교체**: dataloader 가 실제로 소비하는 것 — 우리가 통제하는
pseudo 샘플링 — 을 바꾼다. 어떤 pseudo-label 이 몇 번 노출되는지가 달라지고
**노출 총량(1440 슬롯)은 그대로**라 exposure 계약을 깨지 않는다.

```
build_pseudo_datasets.py --sampling-seed {43,44} --suffix _P{43,44}
R1_NAIVE_P43/P44   unique_PL 924  pseudo/unique 1.56  epoch_entries 2880
R5_PROPOSED_P43/P44 unique_PL 259  pseudo/unique 5.56  epoch_entries 2880
```

R1(naive)과 R5(proposed) 두 arm 으로 좁혔다 — 확인해야 할 것은 "R5 의 우위가
샘플링 산포 안인가" 이므로 그 둘이면 답이 나온다.

개수 효과와 선별 품질 효과를 합쳐서 말하지 않는다.
