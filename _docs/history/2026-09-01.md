### 3. `scripts/stage0/model_compare/yolo26_explain.py` (신규)

"DOPE 는 heatmap 을 보는데 YOLO26 은 시각화가 되나" 라는 질문에 대응.
head 출력을 실측해보니 재구성 가능했다.

```
scores  (1,1,8400)    anchor 별 objectness
kpts    (1,27,8400)   ★anchor 8,400개가 각자 9-keypoint 전체를 예측
feats   80/40/20      백본 특징
```

낸 것: objectness heatmap(3스케일) / feature activation / keypoint vote map
(DOPE belief map 대응) / vote 산포 / anchor 선택 패널.

★삽질 2건 — 둘 다 안 잡으면 결과가 조용히 틀린다:
```
1. scores 가 logit    sigmoid 없이 정규화 -> anchor 1개만 남음 (max 3.14)
2. kpts 가 raw offset  (offset + anchor) * stride 를 안 하면 좌표가 화면 밖
                       -> vote map 이 텅 빔. 산포 0px -> 3~10px 로 바뀜
```

### 4. `scripts/stage0/model_compare/yolo26_anchor_oracle.py` (신규)

"어느 anchor 를 채택하는지 시각화 가능한가" 에서 파생. 그림에 그치지 않고
**선택이 레버인지**를 정본 140장에서 수치화했다.

```
                    median      p90     mean
top-1 (실제)         10.30    39.19    26.75
oracle top-8          8.15    19.02    16.79
상금                  1.83     9.54     9.97

top-1 이 이미 최선     18/140  (12.9%)
상금 > 2px             64/140  (45.7%)
후보 score 폭(median)  0.088
```

읽는 법: 중앙값 상금 1.83px 로 작지만 **꼬리가 크다**(p90 39.2 -> 19.0).
score 는 거의 평평한데(폭 0.088) 답은 최대 12.5px 벌어진다.
★oracle 은 GT 를 보고 고른 것 — 배포 불가, rerank 상한일 뿐이다.

memory `correct-box-bad-keypoint-is-the-bottleneck`(rerank 상금 9장뿐)과
중앙값에서는 같은 방향이나 **꼬리에서는 어긋난다**. 모델·정의가 달라 직접 비교는
못 하지만 봉합하지 않고 남긴다.

### 확인만 하고 코드 변경 없음

- **YOLO26 은 2단계(box -> crop -> keypoint)가 아니다.** `Pose26.forward_head` 에서
  `pose_head` 가 백본 특징 `x` 를 받고, `kpts_decode` 는 anchor·stride 만 쓴다.
  실증: 예측 keypoint 가 예측 box 밖으로 나간 것이 6프레임에서 **19/54(35%)**.
  box 는 "어느 anchor 의 답을 채택할지" 를 고르는 선택 장치일 뿐이다.

- **YOLO26 에 adaptive keypoint uncertainty 가 실재한다.** RLE(Residual
  Log-likelihood Estimation) + RealNVP flow, keypoint 별 sigma_x/sigma_y.
  `error = (pred - gt) / sigma`. 우리 체크포인트에 `cv4_sigma` 12개 +
  `flow_model` 75개가 살아 있고 `rle=1.0` 으로 학습됐다.
  ★단 `if self.training:` 안에서만 출력되고 `fuse()` 가 그 head 를 지운다.
  train 모드 forward 로 꺼내보면 코너별로 값이 다르다(kp5 sy 0.523 vs kp7 0.917).
  **현재 우리 PnP 는 sigma 를 안 쓴다** — 제목에 넣으려면 추론에서 꺼내
  sigma 가중 PnP 로 연결해야 기여가 된다.

### 왜 pose 지표를 안 냈나

R/t/AUC/5cm5 는 **의도적으로 배제**했다. PnP 의 3D 모델을 GT `dimensions_m` 에서
만들기 때문에 평가가 90도 yaw 구분을 대신 풀어준다
(memory `evaluator-receives-gt-per-frame-axis-assignment`, `REPRESENTATION_BLOCK=True`).
여기 낸 검출률·corner px 는 GT 의 2D keypoint 만 쓰므로 그 누수와 무관하다.

corner 는 order-free Hungarian median — 기존 정의를 그대로 쓰고 신설하지 않았다.
population 은 `data_paths.EVAL_CANONICAL` import + `objects[0].split=="eval"`
(164 스캔 -> 140 집계, 정본 수와 일치).
