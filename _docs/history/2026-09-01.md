### 4. `scripts/stage0/model_compare/yolo26_anchor_oracle.py` (신규)

"어느 anchor 를 채택하는지 시각화 가능한가" 에서 파생. 그림에 그치지 않고
**선택이 레버인지**를 정본 140장에서 수치화했다.

```
                    median      p90     mean

```

읽는 법: 중앙값 상금 1.83px 로 작지만 **꼬리가 크다**(p90 39.2 -> 19.0).
score 는 거의 평평한데(폭 0.088) 답은 최대 12.5px 벌어진다.
★oracle 은 GT 를 보고 고른 것 — 배포 불가, rerank 상한일 뿐이다.

memory `correct-box-bad-keypoint-is-the-bottleneck`(rerank 상금 9장뿐)과
중앙값에서는 같은 방향이나 **꼬리에서는 어긋난다**. 모델·정의가 달라 직접 비교는
못 하지만 봉합하지 않고 남긴다.

### 확인만 하고 코드 변경 없음

- **YOLO26 은 2단계(box -> crop -> keypoint)가 아니다.** `Pose26.forward_head` 에서
  `pose_head` 가 백본 특징 `x` 를 받고, `kpts_decode` 는 anchor·stride 만 쓴다.
  실증: 예측 keypoint 가 예측 box 밖으로 나간 것이 6프레임에서 **19/54(35%)**.
  box 는 "어느 anchor 의 답을 채택할지" 를 고르는 선택 장치일 뿐이다.

- **YOLO26 에 adaptive keypoint uncertainty 가 실재한다.** RLE(Residual
  Log-likelihood Estimation) + RealNVP flow, keypoint 별 sigma_x/sigma_y.
  `error = (pred - gt) / sigma`. 우리 체크포인트에 `cv4_sigma` 12개 +
  `flow_model` 75개가 살아 있고 `rle=1.0` 으로 학습됐다.
  ★단 `if self.training:` 안에서만 출력되고 `fuse()` 가 그 head 를 지운다.
  train 모드 forward 로 꺼내보면 코너별로 값이 다르다(kp5 sy 0.523 vs kp7 0.917).
  **현재 우리 PnP 는 sigma 를 안 쓴다** — 제목에 넣으려면 추론에서 꺼내
  sigma 가중 PnP 로 연결해야 기여가 된다.
