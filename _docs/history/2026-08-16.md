### 변경 파일: `challenge/pallet_jetson_deploy/infer_fps.py`

**그리기 경로만 수정.** PnP·keypoint 순서·3D 모델·dims 등 docstring 이 "검증된 로직을
그대로 복제" 라고 못박은 부분은 일절 건드리지 않았다. 이 파일은 Jetson 배포용
standalone 이고 문서 3 곳(`_docs/jetson_nano/02_*`, `_docs/jetson_nano/README.md`,
`pallet_jetson_deploy/README.md`)이 참조하지만 코드로 import 하는 곳은 없다.

```
항목                     Before                      After
──────────────────────────────────────────────────────────────────────────────
yaw 각도                 없음                        yaw_from_R() 신규
roll/pitch               없음                        roll_pitch_yaw_from_R() 신규
방향 화살표 length       (draw_axes 의 XYZ 3축)      draw_yaw_arrow() 2.0 m
화살표 방향              local +Z (far, 화면 안쪽)   local -Z (팔레트 정면)
min_px 폴백              14.0 px                     6.0 px
자세 위젯                없음                        나침반 + 자세계 (우하단 고정)
표시 모드                단일                        --yaw-only 플래그 추가 (기본 불변)
```

**이유**

1. **화살표 방향** — 이 파일의 3D 모델은 near face(0~3, fork-pocket 진입면) = `z=-d/2`
   라서 팔레트 정면이 **local −Z** 다. `draw_axes` 가 그리던 파란 +Z 축은 far face 쪽이라
   항상 소실점 방향으로 뻗었고, 사용자가 "카메라 기준 뒤로 보인다" 고 지적한 게 이것이다.
   실측 근거: 카메라 pitch-down 15°/Z=3m 에서 near 평균 z 2.36m vs far 3.61m.

2. **length 0.6 → 2.0 m** — 0.6m 일 때 553 프레임 중 65.8% 가 14px 미만이라 ⊙ 로
   그려졌다. ⊙ 그룹의 |yaw|(14.3°)·앙각(2.6°)·거리(3.72m)가 전체와 **동일** 했으므로
   원인은 각도가 아니라 거리(median 3.72m) 대비 짧은 길이였다. 2.0m 에서 median 43px.

3. **오일러 순서 = 내재 Y-X-Z** (`R = Ry(yaw) @ Rx(pitch) @ Rz(roll)`) — 이 순서에서만
   `atan2(R02,R22) == yaw` 가 항등이라 기존 `yaw_from_R`(= deployment ψ) 과 값·부호가
   같다. uniform SO(3) 200k 샘플 대조 `0.000e+00°`. 다른 순서를 쓰면 align.py 의
   `ψ>0 → ROT_RIGHT` 분기가 깨진다.

4. **나침반 위젯** — 정면 벡터의 화면 투영은 카메라를 정확히 향할 때 길이가 0 이 되어
   방향이 정의되지 않는다(원리적 한계). 화면좌표계 위젯으로 빼면 원근과 무관하게
   크기가 고정된다. 바늘 = 삽입축(near→far) = 지게차가 향해야 할 heading 이라
   yaw>0 → 바늘 우측 → align.py ROT_RIGHT 와 화면이 자동 일치(부호를 두 번 정의하지 않음).

5. **docstring 정정** — 08-15 에 내가 쓴 "ψ>0 → 팔레트 정면이 카메라 우측" 은 반대다.
   ψ>0 이면 정면 법선은 카메라 **좌측**이고 지게차가 **우회전**해야 한다. 값은 맞으므로
   문구만 고쳤다. 같은 오류 문구가 `pose6d_adapter.py:74`(Korea-Railroad-project) 에도
   있으나 다른 repo 라 미수정 — **남은 TODO**.

### 미해결 / 주의

- **dims 불일치 미수정**: `PALLET_DIMS=(1.1,1.3,0.11)` 이 contract 의 target_synth

- 위 수치는 전부 `forklift_raw_20260528_163408.mp4`(주간·실외) 와

### 추가: 팔레트 위 3축 복원 (`draw_axes` viewer_axes 모드)

사용자 요청 — 우하단 위젯은 두고 팔레트에도 자세 3축을 다시 그릴 것 (yaw 화살표 하나만
있던 상태). 기존 `draw_axes` 를 그대로 되살리면 파란 +Z 가 다시 far(뒤)로 향하므로,
표시 전용 파라미터를 넣었다.

```
draw_axes()              Before                    After
──────────────────────────────────────────────────────────────────────────
시그니처                 (img,R,t,K,length=0.5)    + viewer_axes, labels
X 축                     local +X (right)          동일
Y 축                     local +Y (OpenCV down)    local -Y (up)  ※viewer_axes
Z 축                     local +Z (far, 뒤)        local -Z (front) ※viewer_axes
축 끝 라벨               없음                      X / Y / Z (labels=True)
외곽선                   없음                      검정 4px 밑선 (밝은 배경 대비)
--yaw-only 의 장면 표시  draw_yaw_arrow 2.0m       draw_axes(length=0.9, viewer_axes)
```

`viewer_axes` 는 **표시 방향만** 바꾼다 — R 도 rpy 값도 건드리지 않는다. 기본값 False 라
일반 모드와 Jetson 배포 동작은 그대로다.

Y 를 뒤집는 이유: OpenCV 는 +Y=down 이라 그대로 그리면 축이 화면 아래로 길게 빠져
프레임 밖으로 나간다(1.2m 에서 실제 발생, 프레임 150 눈 검증). 길이도 1.2 → 0.9m 로
줄였다(팔레트 폭 1.1m 기준).

Z 축은 여전히 짧게 보인다 — 정면 벡터라 카메라를 향할수록 투영이 짧아지는 원리적
성질이고, 그 정보는 나침반 위젯이 대신 진다.

```
YOLO(E, task="pose")   boxes=1 conf=0.975   keypoints=(1,9,3)   det 95.8%
```

### Orin Nano 추정 (±50%, 실측 아님)

TRT-FP16@640 은 2.55ms 로 우리 3080 의 1.41ms 대비 **1.8 배** 차이였다 (작은 모델은

외부 실측 보고(Orin Nano, YOLO11n TRT FP16 @640): 4.5ms ~ 13ms 로 편차가 큼.
전력 모드(MAXN)·jetson_clocks·JetPack 버전에 좌우된다.

종합 추정: **순수 추론 5~15ms, 전처리 포함 full pipeline 15~25ms ≈ 40~65 FPS**.

Orin 보드에서 engine 을 빌드해 `infer_fps.py` 를 돌려야 확정된다(engine 은 하드웨어 종속).

### ★ 설계 실수: patience 를 합성 val fitness 에 걸었다

### 데이터 계약 — 실측으로 확정한 것

### 설계 선택 2건 (기록)

### 신규 파일: `scripts/data_prep/debug/_vdo_focal_height_identifiability.py`

1회성 진단이라 `debug/` 의 `_` prefix 규약을 따랐다. `--kps <json>` 으로 임의
keypoint 세트에 재실행 가능. 내부는 전부 `scripts/annotate/annotate_pnp.py` 의
`make_pallet_keypoints_3d` / `solve_pose` 를 재사용한다(3D 모델·convention 미복제).

- `profile()` : 각 f 에서 프레임 공유 H 를 최적화 → H*(f) 프로파일
- `weak_perspective_H()` : focal 이 식에 안 들어가는 affine 폐형식 H
- `f_from_square_vp()` : 정사각 top face 직교 소실점 → f
- pose branch 는 `solve_pose`(cube-flip 열거)로 한 번 고정하고 이후
  `SOLVEPNP_ITERATIVE` warm-start LM 으로만 이동(flat 물체 EPnP 금지 규칙 준수)

함정 1건: `np.array(raw)[:, :2]` 슬라이스는 non-contiguous 라 `cv2.solvePnP` 의
`checkVector` 가 실패한다 → `np.ascontiguousarray` 필요.

- **H 는 결정 가능**. f 를 1.9배(763~1455) 흔들어도 H 는 3.5% 만 움직인다.

  1cm 안에서 일치 → H 는 이미지의 affine 성분(정사각 foreshortening + 상하면 offset)
